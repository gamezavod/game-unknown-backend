# API рабочих смен «3 в ряд»

Шесть серверных ручек для текущего прототипа. Поле, RNG, ходы, заряды, добыча и расчёт награды принадлежат бэкенду. Фронтенд передаёт действия и показывает возвращённые шаги анимации. Зависимости не добавлены; используются штатные FastAPI, PostgreSQL, SQLAlchemy, Alembic и pytest.

Источники правил:

- `client-web/src/match3.ts` и `match3-ui.ts` фронтенда, commit `1c43202c4bbbbb3309cf69bae04b14d4b7f35c8c`;
- предоставленная «Концепция игры.md», разделы «Мини-игры 3 в ряд» и «Расширение острова и раскопки»;
- согласованное решение использовать настройки текущего прототипа там, где численные параметры концепцией не заданы.

## Сессия и установка

Маршруты `/game/match3/*` публичные, без JWT. Используется прежний `player_id` или cookie `game_player_id`. Сначала создайте/откройте мир:

```sh
curl -c cookies.txt -H 'Content-Type: application/json' \
  -d '{"seed":"мой-остров"}' http://localhost:8000/game/session
curl -b cookies.txt http://localhost:8000/game/match3/state
```

Вместо cookie передавайте `?player_id=<UUID>` в каждый запрос. Новый случайный ID на каждом запросе не продолжает прежнюю сессию. Знание ID в этом временном публичном режиме позволяет работать с соответствующим миром; существующие `/auth/*` и `/me` не изменяются.

Перед запуском обновите БД: `uv run alembic upgrade head`. Миграция `004_match3` добавляет `match3_profiles`, `match3_runs` и `match3_receipts`; прежние миры и аккаунты сохраняются. Локальный Docker Compose применяет её существующим сервисом `migrate`. В Swagger `/docs` появился раздел «Рабочие смены match-3».

## Общие поля и правила запросов

- Позиция фишки: `{"row":0,"column":0}`. Индексы **0–7**, сначала строка, затем колонка; это не координаты гекс-карты `q/r`.
- Идентификаторы смен: `sawmill`, `farm`, `quarry`, `mine`, `dig`.
- Ресурсы: `wood`, `food`, `stone`, `iron` (металл/железо текущего фронтенда).
- `runId` — UUID сохранённой партии. Игрок может иметь одну активную партию.
- `serverSavedAt` — подтверждённая серверная метка в миллисекундах Unix, как у API мира. Игровые действия обновляют её в той же транзакции.
- `revision` относится к полю партии. Рекомендуется передавать `expectedRevision` в moves/lightning/finish: устаревшее действие получит 409 и не изменит партию.
- Для сетевых повторов POST рекомендуется заголовок **`Idempotency-Key`**, непустая строка до 128 символов. Повтор того же запроса с тем же ключом возвращает первоначальный ответ, без повторного хода/расхода заряда/начисления. Использование ключа с другим телом или операцией даёт 409. Ключи разделены по игрокам. Поздний повтор возвращает первоначальный снимок; текущую партию читайте через `/state`.
- Фронт не может присылать своё поле, начисляемые ресурсы, бонус или остатки ходов. Лишние поля и неверные типы отклоняются с 422.

## GET /game/match3/state

Тело отсутствует. Возвращает:

```json
{
  "playerId":"<UUID>",
  "serverSavedAt":1790000000000,
  "warehouse":{
    "wood":{"amount":120,"limit":200},
    "food":{"amount":80,"limit":200},
    "stone":{"amount":60,"limit":200},
    "iron":{"amount":0,"limit":200}
  },
  "digDepth":0,
  "excavation":null,
  "shifts":[
    {
      "shiftId":"sawmill","title":"Лесопилка","resourceId":"wood",
      "goal":{"type":"collect","chipId":"log","target":30,"progress":0,"bonus":10,"targetDepth":null},
      "moves":24,"charges":1,"requiredWorkers":1,"assignedWorkers":2,
      "available":true,"reasons":[]
    }
  ],
  "activeRun":null,
  "lastResult":null
}
```

`shifts` всегда содержит все пять смен (в примере показана одна). `reasons` — массив `{code,message}`: `active_run`, `warehouse_full`, `no_workers`, `no_excavation_site`, `unsupported_generator`. Нехватка энергии не запрещает обычную партию, а отключает молнию. При активной смене вместо создания новой надо восстановить `activeRun`.

Для незавершённой раскопки `excavation` содержит `siteId`, позицию участка `q/r`, тип его местности для предварительного просмотра, `depth`, `targetDepth:6`, `paid`. `lastResult` — итог последней завершённой смены. Его остаток склада зафиксирован на момент начисления; верхний `warehouse` отражает текущие запасы.

## POST /game/match3/runs

Тело:

```json
{"shiftId":"sawmill"}
```

Для раскопок можно дополнительно выбрать конкретный соседний участок тумана:

```json
{"shiftId":"dig","target":{"q":4,"r":0}}
```

`target` допустим только для `dig`. Если его нет, используется начатый участок либо первый соседний участок в детерминированном порядке. У незавершённой раскопки сменить участок нельзя; продолжение восстанавливает ту же глубину и факт оплаты.

Ответ **201** — `RunView`:

```json
{
  "playerId":"<UUID>","serverSavedAt":1790000000001,
  "runId":"<UUID>","shiftId":"sawmill",
  "board":[["log","tree","leaf","acorn","mushroom","log","tree","leaf"]],
  "goal":{"type":"collect","chipId":"log","target":30,"progress":0,"bonus":10,"targetDepth":null},
  "movesLeft":24,"chargesLeft":1,"collected":0,
  "loot":{"wood":0,"food":0,"stone":0,"iron":0},
  "digDepth":0,"amphora":null,"revision":0,"status":"active","result":null
}
```

В реальном ответе `board` содержит **8 строк по 8 фишек**; в примере сокращён до одной строки. Начальное поле не содержит готовых совпадений и имеет допустимый обмен. Для `dig` возвращается позиция амфоры (`row = 1 + digDepth`, `column = 3`), сохранённая глубина и цель `type:"amphora", target:1, targetDepth:6`.

Правила партии фиксируются при её создании. Изменение настроек работников/целей во время партии не изменяет уже начатую смену. Пока она активна, следующий start получает 409 `active_run`; повтор с тем же Idempotency-Key возвращает первоначальный run.

## POST /game/match3/runs/{runId}/moves

Тело:

```json
{
  "from":{"row":1,"column":2},
  "to":{"row":0,"column":2},
  "expectedRevision":0
}
```

Ответ **200** включает все поля `RunView` и:

```json
{
  "accepted":true,
  "rejectionReason":null,
  "swappedBoard":[],
  "steps":[
    {
      "kind":"match","before":[],
      "cleared":[{"row":0,"column":0},{"row":0,"column":1},{"row":0,"column":2}],
      "after":[],"earned":3,"amphoraBefore":null,"amphoraAfter":null
    }
  ]
}
```

Пустые массивы в этом примере обозначают сокращённые полные поля 8×8. `swappedBoard` нужен для анимации обмена/возврата. Каждый шаг содержит поле до очистки, координаты очистки, начисленную в этом шаге добычу, поле после падения/дозаполнения и позиции амфоры до/после шага. Шаги непрерывны: `after` предыдущего равен `before` следующего; последний `after` равен итоговому `board`.

Совпадение — от трёх одинаковых по горизонтали/вертикали. Пересечение считается без двойного начисления. Только главная фишка даёт ресурс, по единице за штуку. Неудачный обмен возвращает `accepted:false`, причину `no_match`, `not_adjacent` или `amphora_blocked`, исходное поле и пустые steps. **Ход, RNG, заряд и добыча не меняются**. Неверная координата вне 0–7 — 422.

В раскопках четыре типа фишек: `rock`, `brick`, `sprout`, `autumn`. У камня один ID — `rock`. Старый `digRock` при чтении партии и сохранённых ответов Idempotency-Key приводится к `rock`, включая все кадры каскадов; набор фишек в сохранённых правилах очищается от дубля. Преобразование не тратит ход, не меняет RNG, глубину или revision и не пересоздаёт поле. Старые смешанные камни после загрузки участвуют в одном совпадении. Дополнительная SQL-миграция и сброс сохранений не нужны.

Успешный обмен тратит один ход и разрешает каскады. Когда цель достигнута или закончились ходы, партия автоматически завершается и `result` содержит итог — отдельно вызывать finish для начисления не требуется. Повтор finish всё равно безопасен. Цель проверяется после каждого каскада, как в прототипе. Терминальное поле может содержать неразыгранное совпадение: следующего хода уже нет.

У активного поля всегда есть допустимый обмен. Если его не осталось или сработал лимит 40 каскадов, возвращается отдельный шаг `kind:"reshuffle"`, без очистки/добычи/дополнительного расхода хода. Так клиент получает явную анимацию смены поля, а сервер защищён от бесконечного каскада.

## GET /game/match3/runs/{runId}/hint

Тело отсутствует. Ответ:

```json
{
  "playerId":"<UUID>","runId":"<UUID>","revision":0,
  "available":true,
  "from":{"row":1,"column":2},"to":{"row":0,"column":2}
}
```

Подсказка возвращает допустимый обмен и не изменяет поле, RNG, ходы, заряды, метку сохранения или revision. Для законченной партии — `available:false`, `from:null`, `to:null`. Не нужно применять подсказку к другой revision поля.

## POST /game/match3/runs/{runId}/lightning

Тело:

```json
{"row":3,"expectedRevision":0}
```

Ответ — все поля `RunView`, `cleared` (клетки выбранного ряда) и `steps`. Первый шаг имеет `kind:"lightning"`; последующие каскады, если возникли, также возвращаются для анимации. Добыча всех очисток учитывается сервером. **Обычный ход не расходуется, заряд уменьшается на один**. Если достигнута цель, партия автоматически завершается.

Амфора не очищается молнией; её позиция исключается из cleared. При отсутствии заряда — 409 `no_charges` или `no_energy`, без изменений состояния. По согласованному прототипу заряд есть только у лесопилки; конфигурация других смен оставлена без новых усилителей.

## POST /game/match3/runs/{runId}/finish

Тело отсутствует либо `{"expectedRevision":1}`. Ответ — зафиксированный итог:

```json
{
  "playerId":"<UUID>","serverSavedAt":1790000000002,
  "runId":"<UUID>","shiftId":"sawmill","reason":"early_finish",
  "resourceId":"wood","collected":7,"bonus":0,"total":7,
  "credited":7,"overflow":0,"goalReached":false,
  "warehouse":{
    "wood":{"amount":127,"limit":200},"food":{"amount":80,"limit":200},
    "stone":{"amount":60,"limit":200},"iron":{"amount":0,"limit":200}
  },
  "dig":null
}
```

`reason`: `early_finish`, `goal_reached` или `moves_exhausted`. `collected` — собранное, `bonus` — награда за цель, `total` — их сумма, `credited` — фактическое зачисление с учётом свободного места, `overflow` — сколько не поместилось. Неуспех не отнимает добычу; недостигнутая цель просто не даёт бонус. Повтор finish возвращает прежний итог и прежнюю метку начисления, даже если уже сыграна следующая смена. Он не меняет последнюю награду и не начисляет её снова.

Для раскопок `resourceId:null`, ресурсный склад не пополняется. `dig` содержит `siteId`, достигнутую `depth`, `savedDepth`, `paid`, а при успехе — `finding` и `revealedCell` (`q/r`). Успех добавляет амфору в существующую коллекцию мира и открывает именно выбранный участок. При нехватке ходов/досрочном выходе сохраняются выбранный участок, глубина и оплата. Амфора продвигается на один ряд в каскаде только после очистки клетки прямо под ней; обменивать или включать её в совпадение нельзя.

При старом сохранении, где участок раскопок уже находился на открытой суше, при успехе открывается ближайший соседний туман — совместимость с прежней схемой. Новые участки всегда выбираются в тумане. Текущая раскопка допускается как единственная ещё не открытая координата в `excavationSites`; после завершения она становится открытой клеткой.

## Настройки и границы прототипа

| Смена | Фишка/ресурс | Цель | Бонус | Начальные ходы | Заряды |
| --- | --- | --- | --- | --- | --- |
| sawmill | log → wood | 30 | 10 | 24 | 1 |
| farm | wheat → food | 30 | 10 | 22 | 0 |
| quarry | rock → stone | 30 | 10 | 22 | 0 |
| mine | ore → iron | 30 | 10 | 17 | 0 |
| dig | амфора → находка | 1, глубина 6 | 0 | 20 | 0 |

Параметры находятся в `app/match3/config.py`; запасы и назначения сохраняются отдельно для каждого игрока в Profile. Базовая длина ресурсной смены: 1/2/3 работника → 15/20/25 ходов, плюс бонус счастья (в прототипе +2) и соседнего леса для лесопилки (+2). Начальные назначения: 2/2/2/1 работника. Без работника ресурсная смена недоступна. Полноценная система населения/счастья/энергии пока отсутствует: значения — согласованное состояние прототипа, их будущий engine должен обновлять на сервере под той же блокировкой мира. Фронт не назначает их в этих шести ручках.

Концепция говорит о плате за новые раскопки, её росте, частоте урожая у воды, ступенях развития и лагере археолога, но не задаёт численную цену и коэффициенты выпадения. По согласованному решению новые списания не вводятся: `paid=true`, еда сохраняется. Начальные частоты фишек равномерные, как в коде прототипа; новая модель водного соседства не выдумывалась. Постройка каменоломни/рудника, прогрессия поселения, прирост населения, производство вне игры, усилители за комбинации и образовательные карточки — отдельные системы. Не утверждается, что вся концепция игры уже реализована.

## Транзакции и сохранение

Каждое изменение берёт блокировку строки существующего `world_saves`. Мир, профиль склада, run, итог и idempotency receipt записываются **одной транзакцией**. Уровень БД дополнительно запрещает две активные смены одного игрока. Ошибка откатывает все изменения. Активная партия хранит полное поле, состояние RNG, правила, ходы, заряды, добычу, глубину и revision; после перезапуска восстанавливается без регенерации.

Снимок мира `GET /game/progress` продолжает содержать ландшафт, раскопки и коллекцию. Склады и партия читаются через match3 state. При активной раскопке общий `PUT /game/progress` не может менять/стирать её участок, глубину, оплату и коллекцию в обход match3 API. Завершение match3 уже увеличивает `completedShifts`; не дублируйте его отдельным `completeShift` API мира.

Для резервной копии сервера нужны все таблицы PostgreSQL, а не только JSON мира. Автосейв в браузер и обработчики вкладки относятся к будущему подключению фронтенда, которое в этом изменении не выполнялось. Receipts хранят первоначальные ответы; их операционную очистку следует планировать отдельно, сохраняя ключи активных смен.

## Ошибки и проверка

Ошибки match3: `{ "detail":"...", "code":"..." }`. Основные коды:

- 404: `world_not_found`, `run_not_found` (включая чужой run при другом player_id);
- 409: `active_run`, `warehouse_full`, `no_workers`, `no_energy`, `no_charges`, `run_finished`, `stale_revision`, `idempotency_conflict`, `unfinished_excavation`;
- 400: `invalid_target`;
- 422: стандартная проверка входа, `profile_corrupt`, `run_corrupt`, `receipt_corrupt` — данные сохраняются, автоматического сброса нет.

Проверки выполняются штатно: `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy app tests migrations scripts`, `uv run python scripts/check.py`. Нужна выделенная PostgreSQL-база `_test` по правилам основного README. Проверяются стабильные поля всех пяти тем, каскады и точная добыча, возврат неудачного обмена, чистые подсказки, заряды, атомарность start/move/finish, лимиты склада, бонус/неуспех, повторные запросы, восстановление активной партии, глубина и оплата раскопок, точное открытие выбранной территории и сохранность повреждённых данных. Прежние тесты авторизации и мира тоже остаются в наборе.
