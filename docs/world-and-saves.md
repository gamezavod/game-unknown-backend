# Генерация мира и сохранение прогресса

Модули встроены в **существующий FastAPI-бэкенд**. Используются текущие PostgreSQL, SQLAlchemy, Alembic, JWT, `uv` и pytest. Зависимости и `uv.lock` не изменены. Фронтенд не изменён и к новым маршрутам автоматически не подключается.

## Запуск и проверка API

Запуск выполняется по основному README: `uv sync --frozen`, `uv run alembic upgrade head`, затем `uv run uvicorn app.main:create_app --factory`. В Docker Compose миграции применяет существующий сервис `migrate` перед стартом `api`. Миграция `002_world_progress` добавляет таблицу `world_saves`; `003_guest_worlds` вводит гостевой `player_id`, сохраняя прежние строки и JSON снимков. Для старого острова `playerId` равен прежнему `user_id`. Таблицы авторизации не изменяются.

Игровые маршруты `/game/*` временно работают **без регистрации и JWT**. Swagger `/docs` не требует **Authorize** для этих операций. Существующие `/auth/*` и `/me` сохраняют прежнее поведение.

`POST /game/session` без параметров создаёт гостевой `playerId` и устанавливает cookie `game_player_id`. Браузер и Swagger используют её автоматически. В ответах есть `playerId`; его также можно явно передать в query `?player_id=<UUID>` любого игрового запроса — query имеет приоритет перед cookie. Это позволяет проверять два устройства с одним миром без входа в аккаунт.

`playerId` — публичный идентификатор мира, а не проверка доступа. В текущем режиме любой знающий его может читать и изменять этот мир. Отсутствие ID/cookie при чтении даёт 404; новый мир создаётся только через `/game/session`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/game/session` | Создать мир или вернуть существующий |
| GET | `/game/progress` | Восстановить полный прогресс |
| POST | `/game/actions` | Выполнить действие мира на сервере и сохранить результат |
| PUT | `/game/progress` | Сохранить снимок текущего engine |

Первый запрос:

```json
{"seed":"мой-остров"}
```

Вместо seed можно передать `{}` — сервер назначит случайный seed. Повторный вызов не заменяет существующий остров. Даже при одновременном создании с двух устройств остаётся один мир на `playerId`. Для импорта старого локального сохранения при создании мира предусмотрен `initialSave` — строка версионированного JSON; открытая территория импортируется явно, без регенерации.

Ответы содержат идентификатор игрока и данные для `StorageProvider.load/save`:

```json
{"playerId":"00000000-0000-4000-8000-000000000001","data":"{\"schemaVersion\":2,...}","serverSavedAt":1790000000000}
```

`data` — строка полного сохранения. Отдельная `serverSavedAt` назначается PostgreSQL и является авторитетной. Пример последующего действия:

```json
{
  "action":{"type":"reveal","position":{"q":4,"r":0}},
  "expectedServerSavedAt":1790000000000
}
```

В `/game/actions` поддерживаются:

- `reveal` — открытие соседней туманной клетки;
- `chopForest` — вырубка леса в траву;
- `plantForest` — посадка на свободной траве;
- `advanceGrowth` — учёт роста саженцев;
- `completeShift` — фиксация завершённой игровой смены.

Первые три действия принимают `position`. Поля прежнего DTO `now` и `growthDurationMs` допускаются для совместимости, но не управляют часами и длительностью на сервере. Начало посадки и длительность назначает бэкенд. При входе и чтении прогресса созревшие саженцы автоматически становятся лесом, включая время вне игры.

`PUT /game/progress` принимает:

```json
{
  "data":"{\"schemaVersion\":2,...}",
  "expectedServerSavedAt":1790000000000
}
```

Проверяются схема, координаты, ссылки, соответствие seed/версии текущему миру и отсутствие потери открытых клеток. Для изменения мира предусмотрен `/game/actions`; сохранение снимка позволяет подключить существующий engine и передавать раскопки, здания и коллекцию без добавления отсутствующей игровой механики. Это хранение валидного состояния; защита экономики от поддельного прогресса потребует правил самой экономики.

Ошибки следуют существующему формату `{ "detail": ... }`. При конфликте **409** дополнительно возвращается `current` — целое актуальное сохранение. Неверные параметры/схема — **422**, недопустимое действие — **400**, отсутствие мира — **404**. Игровые маршруты не возвращают 401 из-за отсутствия JWT. Повреждённое/неизвестное сохранение остаётся в базе нетронутым.

## Хранение и конфликты устройств

`world_saves` содержит одну строку на `player_id`: JSONB `data`, `server_saved_at` и необязательную прежнюю связь `user_id` с аккаунтом. Новые гостевые миры не создают пользователей. Текущие типы всех открытых клеток хранятся явно. Генератор используется только при создании мира и открытии новых координат, а не при обычной загрузке.

Запись выполняется под `SELECT ... FOR UPDATE`. Сервер атомарно проверяет `expectedServerSavedAt` в той же транзакции, где записывает новый снимок. Из двух записей с одной исходной меткой проходит одна; другая получает актуальное серверное состояние. Время берётся через PostgreSQL `clock_timestamp()` и монотонно увеличивается для данного сохранения. Клиентские `savedAt`, `revision` и `serverSavedAt` не могут заменить его. Слияния нет; клиент выбирает целый снимок с более свежей подтверждённой серверной меткой.

Каждое серверное действие сохраняется сразу. Неизменённые снимки/действия не вызывают повторную запись и не меняют метку. Два устройства используют один и тот же `player_id`; их cookie и login-сессии могут различаться. Выход из аккаунта не ограничивает публичные игровые маршруты.

Локальный резерв, dirty-интервал 30 секунд, `visibilitychange` и `pagehide` относятся к клиентскому слою. Их обработчики в рамках задачи «только бэкенд» не добавлялись. Фронтенд сможет отправлять снимки в `/game/progress`, а завершение смены — через `completeShift`. На Яндекс Играх гость может использовать локальный резерв; проверка Яндекс SDK и будущая привязка гостевого мира к аккаунту остаются отдельной интеграцией. Cookie выбирает мир и не проверяет права доступа.

Пример запроса без токенов:

```sh
curl -c cookies.txt -H 'Content-Type: application/json' \
  -d '{"seed":"мой-остров"}' http://localhost:8000/game/session
curl -b cookies.txt http://localhost:8000/game/progress
# Либо без cookie, по playerId из первого ответа:
curl 'http://localhost:8000/game/progress?player_id=<UUID>'
```

Откат `003_guest_worlds` допускается только при отсутствии гостевых строк: миграция откажется терять сохранения без аккаунта.

## Схема состояния

Сохранение имеет `schemaVersion: 2`, время действия `savedAt`, подтверждённое серверное время, `revision`, `cloudPending` и `progress`. На сервере `cloudPending=false`; флаг оставлен для совместимости с клиентским резервом.

В `progress` находятся:

- `world`: seed, версия генератора и все открытые клетки с координатами, текущими типами, высотами, зданиями и их уровнями;
- `saplings`: координаты, `plantedAt`, `growthDurationMs`;
- `excavationSites`: открытые участки раскопок;
- `activeExcavation`: `siteId`, `depth`, **`paid`** — факт оплаты начатой раскопки;
- `collection`: идентификаторы предметов, место и время находки;
- `completedShifts`: число завершённых смен.

Ландшафт хранится текущими типами: вырубленный лес — трава, выросшая посадка — лес. История действий для восстановления не нужна. `paid` сохраняется независимо от глубины; при продолжении существующий engine должен использовать это значение вместо повторного списания провизии. Сама экономика и процесс раскопок не добавлены.

Предусмотрена чистая миграция JSON v1 → v2: в v1 прогресс находится в корне, в v2 — внутри `progress`. Это подготовленная схема совместимости; существующий backend до этого миров не хранил. Чтение не меняет исходную строку. Неизвестная версия генератора позволяет загрузить открытые клетки, но запрещает открытие новых с понятной ошибкой.

## Генератор и допущения

`app/world/generator.py` — чистые функции без HTTP, хранилища и часов. Старт — диск радиуса 3, **37 клеток, ровно 25 суши**, без рек. Неизвестные координаты подразумевают туман и не занимают строки в сохранении.

Отдельный валидатор проверяет связность суши, минимум 4 леса, 2 камня, 3 побережья, два леса рядом с лесопилкой и пять допустимых стартовых зданий. Ратуша в центре, дом и склад рядом с ней, лесопилка и ферма на траве; ферма получает клетку у воды, если доступна подходящая. Каждый стартовый уровень — 1. Невалидный кандидат отбрасывается; по умолчанию максимум 128 попыток, затем понятная ошибка. Лимит можно передать аргументом чистой функции.

Вне старта приняты следующие правила, вынесенные в неизменяемый `GenerationConfig`:

- Гладкие поля высоты и влажности строятся по seed, размер региона — 7 гексов.
- Высота ниже 0,38 — вода; соседняя суша — побережье.
- Высота выше 0,69 — горы.
- Полоса влажности 0,5 ± 0,025 на оставшейся суше — река.
- Влажность выше 0,57 — лес, иначе трава.

Приоритет: вода → побережье → горы → река → лес/трава. На границе учитывается исходная стартовая вода. Это простая модель водных полос, без симуляции гидрологии. Возможны проливы и отдельные участки суши одного климата; новые климатические зоны не добавлены.

Жёсткого предела карты нет. Координаты ограничены только диапазоном безопасных целых чисел JavaScript для совместимости DTO. Порядок открытия не влияет на результат. Изменение правил требует новой версии с сохранением старого алгоритма. Арифметика uint32 и UTF-16 обеспечивает совместимость с эталонной реализацией seed, включая Unicode.

Дополнительные настройки в `.env.example`:

| Настройка | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `SAPLING_GROWTH_MS` | `60000` | Длительность новых посадок; записывается у каждого саженца |
| `MAX_SAVE_BYTES` | `10485760` | Максимальный размер строки снимка, не ограничение радиуса карты |

Общий лимит HTTP-запросов следует настраивать на существующем reverse proxy, как описано в основном README.

## Проверки

Используются штатные команды проекта:

```sh
uv run ruff check .
uv run ruff format --check .
uv run mypy app tests migrations scripts
uv run python scripts/check.py
```

`TEST_DATABASE_URL` должен указывать на выделенную базу с именем, заканчивающимся на `_test`: штатная fixture очищает таблицы пользователей и связанный прогресс. `scripts/check.py` применяет Alembic, проверяет отсутствие дрейфа схемы и запускает весь pytest-набор, включая прежние тесты авторизации.

Добавлены проверки 1000 seed, детерминизма, стартовых условий, совместимости seed, ограничения попыток, отсутствия предела радиуса, сохранения открытых клеток и изменений леса, уровней зданий, оплаченных раскопок и коллекции, миграций, повреждённых данных, смены версии генератора, роста вне игры, изоляции пользователей, двух устройств и атомарного конфликта параллельных записей.

## Соответствие критериям ТЗ

| Критерий | Что проверено на бэкенде |
| --- | --- |
| 1. Валидный старт, здания, туман | 1000 seed, 37 клеток радиуса 3, 25 суши, лес/камень/побережье, все пять зданий и соседства проверяются независимо от валидатора генератора. За пределами открытого диска нет сохранённых клеток: там подразумевается туман. |
| 2. Детерминизм | Одинаковый seed даёт одинаковые клетки; порядок открытия не меняет местность. |
| 3. Сохранить → загрузить | PostgreSQL восстанавливает открытые клетки, текущий ландшафт, уровни зданий, посадки и коллекцию; открытые координаты не исчезают. |
| 4. Незавершённые раскопки | `siteId`, `depth` и `paid` переживают запись и чтение без изменений. Расход провизии остаётся обязанностью существующего engine. |
| 5. Версия генератора | Открытые клетки читаются явно; смена версии не регенерирует их. Неизвестная версия блокирует только открытие новой территории. |
| 6. Два устройства | Проверка серверной метки и блокировка строки атомарны; устаревший запрос получает 409 с целым свежим снимком. Слияния нет. |
| 7. Миграции и повреждения | JSON v1 → v2, Alembic 002 → 003 с сохранением прежних данных, отказ от отката с потерей гостевых миров; битые/неизвестные снимки не перезаписываются. |

Полное ТЗ всей игры **ещё не закрыто**: клиентский локальный резерв после действий, dirty-интервал 30 секунд, обработчики вкладки, отображение/открытие тумана в UI и подключение Яндекс SDK требуют интеграции с фронтендом. Здесь предоставлены серверные действия и сохранение снимков; фронтенд по договорённости не изменяется. Наличие тестов API не означает, что эти клиентские сценарии уже работают в игре.
